# Смена транспортного пароля Active Directory при входе в Horizon

Проверка исходников от 24 ноября 2026 года. Для домена Microsoft AD достаточно доработать **Horizon**. Вход и форма смены пароля находятся в одной поставке Horizon 2025.1. Запись уже идёт напрямую в AD по LDAPS. Недостающая часть — определить при входе, что AD требует смены, и проверить то же условие при отправке формы. После смены пользователь проходит обычную аутентификацию через Keystone.

## Что делает поставленный патч

| Действие пользователя | Путь запроса в проверенной версии |
| --- | --- |
| Нажимает «Войти» с доменным паролем | Horizon обращается в Keystone. Переход к штатной форме истёкшего пароля зависит от конкретного текста ошибки Keystone с идентификатором пользователя. Общий отказ LDAP отображается как ошибка учётных данных. |
| Открывает ссылку «Change AD password» | Horizon показывает отдельную форму до входа. Доступность ссылки определяется настройкой функции. При открытии страницы обращения к AD нет. |
| Отправляет форму AD | Horizon подключается к настроенному контроллеру домена под служебной записью, находит DN пользователя, проверяет блокировку, отключение и срок действия учётной записи. Затем выполняет один LDAP Modify для `unicodePwd`. В наборе запрошенных атрибутов отсутствует `pwdLastSet`. |

Следствие видно в существующем тесте. Тестовая запись содержит только `userAccountControl`, `msDS-User-Account-Control-Computed` и `accountExpires`. На такой записи тест ожидает вызова Modify. Поэтому прохождение теста подтверждает отправку операции и объясняет, почему оно ничего не говорит об обязательности смены для конкретного пользователя. [Обработчик входа](https://github.com/openstack/horizon/blob/378addadbed2142f181a6e072caf2f80f538a582/openstack_auth/views.py#L159-L175) · [Разбор ответа Keystone](https://github.com/openstack/horizon/blob/378addadbed2142f181a6e072caf2f80f538a582/openstack_auth/plugin/base.py#L116-L135) · [LDAP-бэкенд формы](https://github.com/lebtmalorny-rgb/horizon/blob/5e85071ad46fc25689b8cd62ffc5eb701a9864e8/patches/0001-Add-opt-in-LDAPS-user-password-change-backend.patch#L88-L155) · [Тест операции](https://github.com/lebtmalorny-rgb/horizon/blob/5e85071ad46fc25689b8cd62ffc5eb701a9864e8/patches/0001-Add-opt-in-LDAPS-user-password-change-backend.patch#L397-L459)

## Что делает Keystone NextGen

Проверен публичный Rust-проект `openstack-experimental/keystone`, ревизия `f198ec5531f726699ad89eefdb4a85d0d5552e84`. Архитектурное решение ADR-0027 закрепляет режим чтения для LDAP и отдельно перечисляет запрет на обновление пароля. [Описание проекта](https://openstack-experimental.github.io/keystone/) · [ADR-0027](https://github.com/openstack-experimental/keystone/blob/f198ec5531f726699ad89eefdb4a85d0d5552e84/doc/src/adr/0027-ldap-identity-driver.md)

| Где проверено | Что происходит |
| --- | --- |
| LDAP, проверка пароля | Драйвер находит DN, выполняет пользовательский bind и преобразует ошибку этого bind в `UserNameOrPasswordWrong`. Диагностический подкод AD для обязательной смены до Horizon по этому пути не доходит. [Исходник](https://github.com/openstack-experimental/keystone/blob/f198ec5531f726699ad89eefdb4a85d0d5552e84/crates/identity-driver-ldap/src/authenticate.rs#L50-L61) |
| LDAP, запись | `update_user_password()` непосредственно возвращает `Readonly`. Обработчик `POST /v3/users/{user_id}/password` сначала проверяет старый пароль и лишь после успеха вызывает метод записи. Для принудительной смены в AD этот API не подходит. [LDAP-драйвер](https://github.com/openstack-experimental/keystone/blob/f198ec5531f726699ad89eefdb4a85d0d5552e84/crates/identity-driver-ldap/src/lib.rs#L527-L536) · [Обработчик API](https://github.com/openstack-experimental/keystone/blob/f198ec5531f726699ad89eefdb4a85d0d5552e84/crates/keystone/src/api/v3/user/password.rs#L61-L84) |
| SQL, первая выдача и административный сброс | При включённом `change_password_upon_first_use` и отсутствии пользовательского исключения SQL-драйвер может назначить паролю срок истечения в момент установки. При входе он проверяет пароль и затем может вернуть `UserPasswordExpired`. Это поведение локальной SQL-записи. [Установка срока](https://github.com/openstack-experimental/keystone/blob/f198ec5531f726699ad89eefdb4a85d0d5552e84/crates/identity-driver-sql/src/password.rs#L118-L138) · [Проверка при входе](https://github.com/openstack-experimental/keystone/blob/f198ec5531f726699ad89eefdb4a85d0d5552e84/crates/identity-driver-sql/src/authenticate.rs#L132-L155) |

В Python Keystone 27.0.0 (Epoxy) результат для AD тот же. Исключение пользовательского bind превращается в общий отказ `Invalid user / password`, а LDAP-метод `change_password()` явно возвращает `Forbidden`. Включение штатной формы Horizon для истёкших паролей этих двух свойств не меняет. [Проверка пользователя](https://github.com/openstack/keystone/blob/27.0.0/keystone/identity/backends/ldap/core.py#L59-L78) · [Метод записи](https://github.com/openstack/keystone/blob/27.0.0/keystone/identity/backends/ldap/core.py#L172-L176)

## Как подтвердить требование смены

Для обычной доменной учётной записи AD значение `pwdLastSet=0` при снятом флаге `UF_DONT_EXPIRE_PASSWD` (`0x10000`) означает, что при следующем входе пользователь должен установить новый пароль. Администратор может выставить это состояние при первичной выдаче и при последующем сбросе. Код AD `data 773` относится к обязательной смене, `532` — к истечению срока, `52e` — к неверным учётным данным. Один общий LDAP-код `49` недостаточен для выбора формы. [Microsoft о pwdLastSet](https://learn.microsoft.com/en-us/windows/win32/adschema/a-pwdlastset) · [Microsoft об установке требования смены](https://learn.microsoft.com/en-us/windows/win32/adsi/user-must-change-password-at-next-logon) · [Таблица подкодов AD](https://support.hpe.com/hpesc/public/docDisplay?docId=sd00007012en_us&docLocale=en_US&page=GUID-F1F98259-8ECD-4881-97BF-3406B67EEE57.html)

Пример из работающего продукта — LDAP-маппер Keycloak для Microsoft AD. В версии 26.4.7 он запрашивает `pwdLastSet` и `userAccountControl`, разбирает диагностику пользовательского bind и в режиме `WRITABLE` для `773` или `532` назначает действие `UPDATE_PASSWORD`. Для Horizon с требованием смены именно транспортного пароля применим принцип выбора действия по сигналу каталога. Ветка `532` относится к отдельной политике обычного истечения паролей. [Чтение атрибутов](https://github.com/keycloak/keycloak/blob/26.4.7/federation/ldap/src/main/java/org/keycloak/storage/ldap/mappers/msad/MSADUserAccountControlStorageMapper.java#L69-L79) · [Обработка результата bind](https://github.com/keycloak/keycloak/blob/26.4.7/federation/ldap/src/main/java/org/keycloak/storage/ldap/mappers/msad/MSADUserAccountControlStorageMapper.java#L129-L174)

Если требуется подтвердить **первую в истории выдачу пароля**, нужен факт создания и выдачи из системы управления учётными записями с привязкой к конкретному объекту AD. Если требуется подтвердить **первый успешный вход именно в Horizon**, нужен полный учёт таких входов в Horizon. Это два разных события. Например, AD ведёт `lastLogon` отдельно на каждом контроллере и охватывает входы в домен из разных приложений. Для формы по одному лишь признаку AD точная надпись — «Требуется сменить доменный пароль». [Microsoft о lastLogon](https://learn.microsoft.com/en-us/windows/win32/adschema/a-lastlogon)

## Как должен проходить вход после доработки Horizon

1. Пользователь вводит домен, логин и текущий пароль в обычной форме входа. Только для домена, настроенного для прямой интеграции с AD, Horizon по проверенному LDAPS читает состояние записи на заданном контроллере. При обычном состоянии пароль проверяет Keystone. Так одна ошибка в обычном пароле не порождает две попытки пользовательского bind.
2. Если каталог показывает обязательную смену и учётная запись доступна, Horizon проверяет результат пользовательского bind для представленных данных. При ожидаемом для данного контроллера ответе AD `49 / data 773` Horizon открывает ограниченный шаг смены. При неверном пароле, нечитаемом состоянии или неоднозначном ответе переход закрыт. Вывод формы по одному логину раскрыл бы состояние чужой записи. Доступ к проекту на этом шаге ещё закрыт.
3. Шаг привязан на сервере к сессии, домену и найденному объекту AD, действует короткое время и завершается после использования. Пароли между запросами не сохраняются. В форме пользователь вводит транспортный пароль повторно и задаёт новый. Обработчик POST проверяет привязку и ещё раз читает состояние того же объекта на том же контроллере. Прямая отправка формы без этого шага не должна запускать запись.
4. Horizon выполняет один LDAP Modify на защищённом соединении с доступным для записи контроллером. Для `unicodePwd` передаются `DELETE` старого значения и `ADD` нового. AD проверяет текущий пароль и право учётной записи изменить собственный пароль. Служебное соединение не является подтверждением знания пароля пользователем. Право административного сброса этой операции не требуется. При потере ответа после отправки результат остаётся неопределённым, автоматически повторять Modify нельзя. [Протокол Microsoft MS-ADTS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/6e803168-f140-4d23-b2d3-c3a8ab5917d2)
5. После подтверждённой записи пользователь входит в Horizon с новым паролем через Keystone и проходит остальные настроенные проверки, включая MFA. На стенде отдельно проверяется снятие условия `pwdLastSet=0` и доступ к назначенному проекту.

## Что проверить на целевом домене

| Тестовая ситуация | Какими наблюдениями подтвердить результат |
| --- | --- |
| Новая учётная запись с требованием смены и верным транспортным паролем | До входа на выбранном DC видно `pwdLastSet=0` и отсутствует `UF_DONT_EXPIRE_PASSWD`. Получен ожидаемый подкод пользовательского bind. До смены доступа в проект нет. После LDAP Modify DC подтверждает успех, `pwdLastSet` становится положительным, вход с новым паролем открывает проект. |
| Та же учётная запись с ошибкой в транспортном пароле | Общий отказ. Признак обязательной смены не раскрывается. Шаг смены не выдан, вызов Modify отсутствует. |
| Обычная действующая запись или только истечение по возрасту (`532`) | Действующая запись входит обычным путём. Истечение по возрасту не обозначается как первичная выдача пароля. |
| Ранее работавший пользователь после административного сброса с требованием смены | AD снова может вернуть `773`. При учёте первичной выдачи событие должно быть классифицировано как повторный сброс. |
| Отключённая, заблокированная или истёкшая учётная запись, недоступный либо нечитаемый признак | Форма не выдаёт шаг обязательной смены и не изменяет каталог. |
| Ссылка открыта напрямую либо состояние изменилось до отправки формы | Сервер не принимает запись без действующего шага или при снятом требовании смены. |

Для сверки с администратором AD можно прочитать состояние тестовой записи до и после смены на том же DC. Значения в угловых скобках заменяются именами стенда.

```powershell
Get-ADUser -Server '<dc-fqdn>' -Identity '<test-sAMAccountName>' -Properties pwdLastSet,userAccountControl |
    Select-Object SamAccountName,Enabled,pwdLastSet,
        @{Name='DontExpirePassword';Expression={($_.userAccountControl -band 0x10000) -ne 0}}
```

Локально повторно выполнены два существующих тестовых модуля Horizon для LDAP-бэкенда и формы на ревизии `14a2de4a110ccae388869b2958ec426318768551`. Результат — 32 теста и 29 подтестов прошли. LDAP-соединение в них замещено тестовым объектом. Проверены исходники и поведение существующей версии с подменой каталога. Сквозная проверка перехода при входе, реальной смены пароля и выдачи доступа на целевой AD остаётся стендовой задачей после доработки.
