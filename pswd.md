Для **OpenStack Epoxy 2025.1 + Microsoft Active Directory** ваш сценарий вполне реализуем. Причём архитектура, которую вы описали, во многом уже заложена в стандартных Keystone и Horizon.

Я проверил исходный код ветки `stable/2025.1`. Самое важное открытие: **в Horizon уже существует механизм принудительной смены пароля при входе, включая отдельную форму. В Keystone уже существует API смены пароля без получения токена.** Основные доработки потребуются именно в LDAP-бэкенде Keystone.

Предлагаю максимально сохранить существующую архитектуру OpenStack, не создавать отдельный сервис смены паролей и не подключать Horizon напрямую к Active Directory.

# 2. Особенности Microsoft Active Directory

Для MS AD я бы не стал реализовывать RFC 3062 как основной механизм. В данном случае необходимо использовать спецификацию Microsoft **MS-ADTS, раздел 3.1.1.3.1.5.1 — unicodePwd**.

| Операция                  | OpenLDAP                           | Microsoft AD DS                         |
| ------------------------- | ---------------------------------- | --------------------------------------- |
| Признак временного пароля | `pwdReset`                         | `pwdLastSet = 0`                        |
| Обязательная смена        | `pwdMustChange`                    | User must change password at next logon |
| Ответ при первом входе    | Password Policy control            | LDAP error 49, data 773                 |
| Истёкший пароль           | `passwordExpired (0)`              | LDAP error 49, data 532                 |
| Смена пароля              | RFC 3062                           | LDAP Modify `unicodePwd`                |
| Административный сброс    | Password Modify без старого пароля | LDAP Modify `REPLACE`                   |

Microsoft документирует смену пароля через `unicodePwd`, а требование смены при следующем входе — через `pwdLastSet`.

## 2.1. Коды ошибок Active Directory

При попытке выполнить LDAP Bind с транспортным паролем контроллер домена обычно возвращает ошибку `LDAP_INVALID_CREDENTIALS (49)` с дополнительным диагностическим кодом.

| AD data code (HEX) | Причина                            | Действие Keystone               |
| ------------------ | ---------------------------------- | ------------------------------- |
| `52e`              | Неверный пароль                    | Отказ во входе                  |
| **`773`**          | Требуется смена пароля             | Перенаправление на смену пароля |
| **`532`**          | Пароль просрочен                   | Перенаправление на смену пароля |
| `533`              | Пользователь отключён              | Отказ во входе                  |
| `775`              | Пользователь заблокирован          | Отказ во входе                  |
| `701`              | Срок действия учётной записи истёк | Отказ во входе                  |
| `530`              | Ограничение по времени входа       | Отказ во входе                  |
| `531`              | Ограничение по рабочей станции     | Отказ во входе                  |

Для вашей задачи ключевыми являются именно `773` и `532`. Не нужно определять необходимость смены пароля только чтением `pwdLastSet`: наличие этого атрибута не подтверждает корректность введённого пользователем пароля.

## 4.2. Доработка LDAP-аутентификации

Файл: keystone/identity/backends/ldap/core.py

Класс:

```
class Identity(base.IdentityDriverBase):
```

Метод:

```
def authenticate(self, user_id, password):
```

В стандартной реализации Keystone пытается выполнить Bind от имени пользователя:

```
conn = self.user.get_connection(    user_ref['dn'],    password,    end_user_auth=True)
```

Но при возникновении исключения причина ошибки LDAP теряется — драйвер возвращает общее сообщение о некорректных учётных данных.

Необходимо отдельно перехватывать `ldap.INVALID_CREDENTIALS` и анализировать дополнительное поле `info`.

Например, создать вспомогательную функцию:

```
import redef get_ad_error_code(exc):    if not exc.args:        return None    details = exc.args[0]    if not isinstance(details, dict):        return None    info = details.get("info", "")    if isinstance(info, bytes):        info = info.decode("utf-8", errors="replace")    match = re.search(        r"\bdata\s+([0-9a-f]+)\b",        info,        re.IGNORECASE,    )    return int(match.group(1), 16) if match else None
```

В обработчике LDAP-аутентификации добавить следующую логику:

```
except ldap.INVALID_CREDENTIALS as exc:    code = get_ad_error_code(exc)    if self.conf.ldap.ad_password_change_enabled:        if code in (0x773, 0x532):            raise exception.PasswordExpired(                user_id=user_id            ) from None    raise AssertionError(        _("Invalid user / password")    ) from None
```

Это фрагмент проектируемой реализации, а не готовый патч. Его следует встроить в существующий метод с сохранением проверок пользователя и освобождения LDAP-соединения.

Также необходимо обеспечить, чтобы ошибки подключения, TLS и недоступности AD не интерпретировались как необходимость смены пароля.

## 4.3. Использовать существующее исключение Keystone

В Keystone уже есть исключение:

```
exception.PasswordExpired
```

Оно наследуется от `Unauthorized` и возвращает HTTP 401 с сообщением установленного формата. Именно это сообщение уже умеет обрабатывать Horizon.

Но здесь есть существенный нюанс: **LDAP ID пользователя и публичный Keystone User ID могут различаться.**

Identity Manager передаёт LDAP-драйверу локальный `entity_id`, а Horizon нужен публичный `user_id`, используемый в Keystone API.

Поэтому в файле `keystone/identity/core.py`, в методе `Manager.authenticate()`, необходимо преобразовать исключение:

```
try:    ref = driver.authenticate(entity_id, password)except exception.PasswordExpired:    raise exception.PasswordExpired(        user_id=user_id    ) from None
```

Так Horizon получит правильный идентификатор для последующего вызова API смены пароля. Для AD-доменов с ID mapping это особенно важно.

## 4.4. Сохранение диагностического кода LDAP

Файл: keystone/identity/backends/ldap/common.py

Здесь обнаружилось ещё одно важное ограничение. В методе `BaseLdap.get_connection()` исключение `ldap.INVALID_CREDENTIALS` преобразуется в `LDAPInvalidCredentialsError`.

При этом диагностический код AD теряется ещё до попадания в `Identity.authenticate()`.

Поэтому перехвата `ldap.INVALID_CREDENTIALS` только в `ldap/core.py`, как в иллюстративном фрагменте выше, недостаточно.

Предлагаю расширить `LDAPInvalidCredentialsError`, добавив внутреннее поле `ad_error_code`, а в `BaseLdap.get_connection()` реализовать:

```
except ldap.INVALID_CREDENTIALS as exc:    error = exception.LDAPInvalidCredentialsError()    error.ad_error_code = (        get_ad_error_code(exc)        if end_user_auth else None    )    raise error from None
```

После этого в `Identity.authenticate()` перехватывать уже `exception.LDAPInvalidCredentialsError`:

```
except exception.LDAPInvalidCredentialsError as exc:    if self.conf.ldap.ad_password_change_enabled:        if exc.ad_error_code in (0x773, 0x532):            raise exception.PasswordExpired(                user_id=user_id            ) from None    raise AssertionError(        _("Invalid user / password")    ) from None
```

Поле `ad_error_code` лучше инициализировать непосредственно в классе исключения. Диагностику служебного LDAP Bind нельзя трактовать как требование смены пароля конечного пользователя.

## 4.5. Доработка Identity Manager

Файл: keystone/identity/core.py

В Keystone Epoxy уже существует метод:

```
Manager.change_password(    user_id,    original_password,    new_password,    initiator=None)
```

Его текущий алгоритм:

1. Проверить старый пароль через аутентификацию.
2. Разрешить продолжение при `PasswordExpired`.
3. Определить identity driver.
4. Проверить новый пароль.
5. Вызвать метод драйвера.
6. Выполнить аудит и отзыв токенов.

Проблема заключается в том, что драйвер получает только новый пароль:

```
driver.change_password(entity_id, new_password)
```

Для Microsoft AD обязательно передавать и старый пароль, поскольку контроллер домена должен проверить его непосредственно при выполнении операции смены.

Есть два варианта реализации.

| Вариант                                | Особенность                                                      |
| -------------------------------------- | ---------------------------------------------------------------- |
| Изменить сигнатуру `change_password()` | Потребуется изменить SQL, LDAP и потенциально сторонние драйверы |
| Добавить отдельный метод драйвера      | Позволяет сохранить обратную совместимость                       |

Я рекомендую второй вариант.

В `keystone/identity/backends/base.py` добавить метод:

```
def change_password_with_original(    self,    user_id,    original_password,    new_password,):    return self.change_password(        user_id,        new_password,    )
```

LDAP-драйвер переопределит данный метод, а SQL продолжит работать через существующую реализацию.

В Identity Manager заменить вызов на:

```
driver.change_password_with_original(    entity_id,    original_password,    new_password,)
```

Остальную логику `Manager.change_password()`, включая проверку старого пароля, обработку `PasswordExpired`, аудит и отзыв токенов, сохранить.

## 4.6. Реализация смены пароля в LDAP-драйвере

В стандартном Keystone LDAP-драйвер запрещает смену пароля:

```
def change_password(self, user_id, new_password):    raise exception.Forbidden(        READ_ONLY_LDAP_ERROR_MESSAGE    )
```

Не нужно разрешать произвольную запись в LDAP. Достаточно реализовать строго ограниченную операцию смены пароля.

### Как выполняется смена пароля в Microsoft AD

Microsoft AD различает две принципиально разные операции:

**Password Change**

Самостоятельная смена

---

LDAP Modify

DELETE unicodePwd

Старый пароль

ADD unicodePwd

Новый пароль

AD проверяет старый пароль.

Нужный вам вариант

**Password Reset**

Административный сброс

---

LDAP Modify

REPLACE unicodePwd

Новый пароль

Старый пароль не проверяется.

Не использовать в этом сценарии

Обе операции описаны в спецификации Microsoft MS-ADTS.

Транспортный пароль, который пользователь знает, необходимо именно **сменить**, а не административно сбросить.

### Пример реализации операции

```
import ldapdef encode_ad_password(password):    return f'"{password}"'.encode("utf-16-le")def change_ad_password(    connection,    user_dn,    original_password,    new_password,):    modifications = [        (            ldap.MOD_DELETE,            "unicodePwd",            [encode_ad_password(original_password)],        ),        (            ldap.MOD_ADD,            "unicodePwd",            [encode_ad_password(new_password)],        ),    ]    connection.modify_s(        user_dn,        modifications,    )
```

Обе модификации передаются в рамках **одного LDAP Modify Request**. Python-ldap выполняет необходимое протокольное BER-кодирование.

## 4.7. От имени кого выполнять LDAP Modify

Это один из самых важных архитектурных вопросов.

При вводе транспортного пароля AD возвращает `773`, поэтому успешного LDAP Bind от имени пользователя нет. Использовать полученную пользовательскую LDAP-сессию невозможно.

Предлагаемый вариант — выполнить LDAP Modify через служебную LDAP-сессию Keystone:

```
LDAP Bind: service account
LDAP Modify: target user's DN
Operation: DELETE old + ADD new
```

Контроллер AD при этом проверяет текущий пароль целевого пользователя и необходимые права на смену пароля.

Следует проверить права `User-Change-Password` для целевых объектов AD и фактическую возможность выполнения операции через используемую служебную учётную запись.

Не следует выдавать ей без необходимости:

- Domain Admin.
- Reset Password (`User-Force-Change-Password`).
- GenericAll на пользовательские объекты.
- Право произвольного изменения `userAccountControl`.
- Право снятия требования смены через `pwdLastSet`.

Работоспособность этого варианта с вашими ACL и версией Windows Server необходимо подтвердить на тестовом AD.

## 4.8. Критическая доработка LDAP-обёртки

В файле `keystone/identity/backends/ldap/common.py` имеется класс:

```
class KeystoneLDAPHandler(LDAPHandler):
```

Его существующий `modify_s()` нельзя без изменений использовать для `unicodePwd`.

При проверке исходников Keystone 27.0.0 обнаруживаются две проблемы:

- Метод преобразует значения LDAP-атрибутов в текстовые строки, а затем в UTF-8. Это нарушит бинарное представление UTF-16LE.
- В debug-логах он маскирует `userPassword`, но не `unicodePwd`. Это создаёт риск утечки паролей.

Рекомендую добавить отдельный узкоспециализированный метод в `KeystoneLDAPHandler`:

```
def change_ad_password(    self,    dn,    original_password,    new_password,):    old_value = (        f'"{original_password}"'.encode("utf-16-le")    )    new_value = (        f'"{new_password}"'.encode("utf-16-le")    )    modlist = [        (            ldap.MOD_DELETE,            "unicodePwd",            [old_value],        ),        (            ldap.MOD_ADD,            "unicodePwd",            [new_value],        ),    ]    return self.conn.modify_s(dn, modlist)
```

Так операция передаётся нижележащему LDAP handler без обычного преобразования значений в UTF-8 и без логирования содержимого модификации.

Также следует исключить запись паролей на уровне самой LDAP-библиотеки, HTTP debug-логов и трассировки запросов.

На первом этапе **не нужно создавать новый REST API**.

## 5.1. Запрос на аутентификацию

Horizon отправляет стандартный запрос:

```
POST /v3/auth/tokens
Content-Type: application/json
```

```
{
    "auth": {
        "identity": {
            "methods": ["password"],
            "password": {
                "user": {
                    "name": "ivanov",
                    "domain": {
                        "name": "AD"
                    },
                    "password": "temporary-password"
                }
            }
        }
    }
}
```

При получении от AD кода `773` Keystone должен вернуть существующую ошибку `PasswordExpired`.

```
HTTP/1.1 401 Unauthorized
Content-Type: application/json
```

```
{
    "error": {
        "code": 401,
        "title": "Unauthorized",
        "message": "The password is expired and needs to be changed for user: USER_ID."
    }
}
```

Этот формат уже совместим с существующей логикой Horizon.

## 5.2. Запрос на смену пароля

Использовать стандартный endpoint:

```
POST /v3/users/{user_id}/password
Content-Type: application/json
```

```
{
    "user": {
        "original_password": "temporary-password",
        "password": "new-password"
    }
}
```

При успешной смене:

```
HTTP/1.1 204 No Content
```

Данный API официально поддерживает смену пароля без токена аутентификации.

Это позволяет решить проблему первого входа без выдачи специального токена или создания отдельной временной авторизованной сессии.

## 5.3. Обработка ошибок смены пароля

Предлагаемое отображение результатов LDAP Modify:

| Ошибка                    | HTTP | Сообщение пользователю                           |
| ------------------------- | ---- | ------------------------------------------------ |
| Неверный старый пароль    | 401  | Неверный текущий пароль                          |
| Нарушение политики AD     | 400  | Новый пароль не соответствует требованиям домена |
| Смена запрещена политикой | 403  | Обратитесь к администратору                      |
| Функция отключена         | 403  | Смена пароля недоступна                          |
| AD недоступен             | 503  | Сервис временно недоступен                       |
| Успешная смена            | 204  | Пароль успешно изменён                           |

Например, код AD `0x52D` соответствует ограничению парольной политики.

Не следует передавать пользователю необработанные диагностические сообщения контроллера домена. Также нельзя все ошибки `ldap.UNWILLING_TO_PERFORM` считать нарушением сложности пароля — необходимо различать причины.

# 6. Что необходимо доработать в Horizon

Здесь объём работ значительно меньше.

## 6.1. Существующий механизм обработки PasswordExpired

Файл: openstack_auth/plugin/base.py

В методе `BasePlugin.get_access_info()` уже предусмотрено распознавание сообщения Keystone об истёкшем пароле регулярным выражением.

После распознавания Horizon формирует:

```
exceptions.KeystonePassExpiredException
```

И сохраняет в исключении `user_id`.

Поэтому при правильном ответе Keystone этот механизм заработает и для пользователей MS AD.

## 6.2. Перенаправление на форму смены пароля

Файл: openstack_auth/views.py

Метод `login()` уже перехватывает `KeystonePassExpiredException` и перенаправляет пользователя на существующий маршрут `password`.

```
reverse("password", args=[exc.user_id])
```

Также уже реализован класс:

```
class PasswordView(edit_views.FormView):
```

После успешного изменения пароля он перенаправляет пользователя обратно на страницу входа.

| Keystoneauth              | Нет                          |
| Keystoneclient            | Нет                          |
| Миграция БД               | Не нужна                     |

Используется существующее исключение `PasswordExpired` как для кода `773`, так и для `532`.

## Вариант 2. Структурированные ошибки

Более чистый API-контракт для долгосрочной поддержки собственного форка.

---

Keystone возвращает не только текст сообщения, но и машиночитаемую причину.

```
{
    "error": {
        "code": 401,
        "title": "Unauthorized",
        "message": "Password change required",
        "error_code": "PASSWORD_CHANGE_REQUIRED",
        "reason": "CHANGE_AFTER_RESET",
        "user_id": "USER_ID"
    }
}
```

Horizon анализирует `error_code` и `reason`, а не регулярное выражение по тексту ошибки.

Второй вариант позволяет различать `CHANGE_AFTER_RESET` и `PASSWORD_EXPIRED`, не зависеть от текста и локализации сообщения.

Однако это уже расширение контракта Keystone API. Потребуется доработать сериализацию ошибок Keystone, обработку HTTP-ответа в Horizon и проверить совместимость с keystoneauth1. Для первой реализации это необязательно.

# 8. Требования безопасности

Учитывая, что Keystone будет менять пароль доменной учётной записи, я бы включил следующие требования в техническое задание.

| Требование                        | Реализация                                   |
| --------------------------------- | -------------------------------------------- |
| Защита канала                     | HTTPS и LDAPS либо StartTLS                  |
| Проверка сертификатов             | Обязательная                                 |
| Проверка старого пароля           | На стороне AD при LDAP Modify                |
| Выдача токена до смены            | Запрещена                                    |
| Хранение паролей в Django Session | Запрещено                                    |
| Хранение паролей в cookies        | Запрещено                                    |
| Пароли в логах                    | Запрещены                                    |
| LDAP `MOD_REPLACE`                | Запрещён в self-service сценарии             |
| Проверка пользователя и домена    | Обязательна также в password API             |
| CSRF-защита формы                 | Обязательна                                  |
| Защита от перебора                | Rate limiting на API и login                 |
| Отзыв существующих токенов        | Сохранить механизм Keystone                  |
| MFA                               | Повторная штатная аутентификация после смены |

Особенно важно, чтобы прямой вызов API смены пароля не позволял обойти проверку заблокированного пользователя, отключённого домена или LDAP-фильтра доступа.

Не нужно включать `common_ldap.WRITABLE = True`. Это внутренний механизм тестирования LDAP-бэкенда, а не поддерживаемая настройка для продуктивной эксплуатации.
